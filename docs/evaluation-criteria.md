# 評分標準

## 五維度評分體系

| 維度 | 權重 | 說明 |
|---|---|---|
| 功能完整性 | 25% | 核心功能是否全部實作且可用 |
| 付費流程 | 25% | 用戶能不能成功付錢 |
| 用戶體驗 | 20% | 30 秒內能否理解產品價值 |
| 程式碼品質 | 15% | 可維護、無安全漏洞 |
| 差異化 | 15% | 跟競品相比有什麼不同 |

## 各維度詳細評分標準

### 功能完整性（25%）

| 分數 | 標準 |
|---|---|
| 1 | 核心功能缺失，無法完成主要用途 |
| 2 | 核心功能部分可用，但有嚴重 bug |
| 3 | 基本功能可用，有小 bug 但不影響主流程 |
| 4 | 所有功能完善，邊界情況有處理 |
| 5 | 功能完善 + 超出預期的貼心細節 |

### 付費流程（25%）

| 分數 | 標準 |
|---|---|
| 1 | 無法付費，或付費後不能開通服務 |
| 2 | 能發起付費但流程會中斷 |
| 3 | 能完成付費但體驗不順（跳轉混亂、無確認） |
| 4 | 付費流程順暢，有確認頁和成功提示 |
| 5 | 付費體驗優秀，有試用提醒、到期通知、升級引導 |

### 用戶體驗（20%）

| 分數 | 標準 |
|---|---|
| 1 | 進入頁面後完全不知道這是什麼 |
| 2 | 需要超過 1 分鐘才能理解產品 |
| 3 | 30-60 秒能理解，但操作不直觀 |
| 4 | 30 秒內理解價值，操作直觀 |
| 5 | 一眼看懂 + 首次使用就有「哇」的感覺 |

### 程式碼品質（15%）

| 分數 | 標準 |
|---|---|
| 1 | 有安全漏洞（XSS/CSRF/注入/憑證洩露） |
| 2 | 無安全漏洞但代碼混亂，無法維護 |
| 3 | 可維護，有基本的錯誤處理 |
| 4 | 結構清晰、TypeScript 型別完整、有測試 |
| 5 | 乾淨、安全、可擴展、有完整測試覆蓋 |

### 差異化（15%）

| 分數 | 標準 |
|---|---|
| 1 | 跟免費競品功能完全相同 |
| 2 | 有微小差異但用戶感知不到 |
| 3 | 有明確差異但不足以成為付費理由 |
| 4 | 差異化足以讓部分用戶願意付費 |
| 5 | 獨特賣點明確，市面上沒有直接替代品 |

## 計算公式

```
總分 = 功能完整性 × 0.25 + 付費流程 × 0.25 + 用戶體驗 × 0.20 + 程式碼品質 × 0.15 + 差異化 × 0.15
```

## 決策門檻

| 總分 | 決定 |
|---|---|
| ≥ 4.0 | ✅ 上線 |
| 3.5 - 3.9 | 🔧 小修後上線（只修關鍵問題） |
| 3.0 - 3.4 | 🔄 打回重做 |
| < 3.0 | ❌ 考慮砍掉這個方向 |

## 一票否決項

以下情況無論總分多高，直接打回：
- 付費流程無法完成（付了錢沒開通）
- 存在安全漏洞
- 首頁加載超過 5 秒
- 手機端完全不能用

## Evaluator 行為準則

1. **預設立場是「沒通過」** — 需要看到充分證據才給高分
2. **不受 Generator 影響** — 不看 Generator 的自測結果
3. **像真實用戶測試** — 不看源碼，用 UI 操作
4. **每個分數都要有理由** — 不能給分不說明
5. **關鍵問題和建議改善要分開** — 關鍵問題必修，建議可後續
